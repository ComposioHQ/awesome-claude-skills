# 示例：一次真实的三方对抗评审

> 这是 skill 完整跑完一遍后的**产出样例**，帮你建立预期。
> 为了篇幅，蓝军报告只保留 3 条缺陷，实际运行通常会产出 5-15 条。
> 另注：本样例产于 v2.1「Token 纪律」之前，故未体现"🟡 一行带位置""T 项总表"等后续格式要求。

> ⚠️ **行号已失效（这本身就是一个教学案例）**
> 本示例记录的是对 **v1.0**（255 行）的评审。该评审直接导致了 v1.1 与 v2.0 的整改，
> 而**整改本身让所有行号发生了位移**——下面引用的 `SKILL.md:163`、`:250` 等在当前版本
> 已指向完全不同的内容。
>
> 这不是疏漏，而是本 skill 反复强调的真实翻车点：**改了代码，文档里引用的行号必然失效**。
> 正确做法是像本文件一样**显式声明失效**，而不是让读者以为引用仍然有效。
> 需要看当前实现时，请用关键词搜索（如搜「不能复用蓝军做裁定」），不要依赖行号。

**注意**：本示例审的不是别人，正是**这个 skill 自己的 `SKILL.md`**（v1.0）。
用 skill 自己的标准审自己，是最能说明它有效性的方式——因为下面这条 🔴 缺陷，正是靠 skill 第 3 步「中立裁定」的标准抓出来的。

仓库：      adversarial-review

声称已完成：三方流程闭环、角色约束齐备、归档策略明确

## 蓝军报告（片段）

### 缺陷总表

| 编号 | 级别 | 定级依据 | 一句话 | 维度 | 位置（文件:行号） |
|---|---|---|---|---|---|
| B1 | 🔴 | 实测（原文对照） | 第 3 步让蓝军自己裁定第三方意见，与"禁止复用 agent"的核心原则自相矛盾 | 治理 | `SKILL.md:163` |
| B2 | 🟠 | 实测（原文对照） | `description` 缺少英文触发词，面向国际社区时无法被英文表述激活 | 可用性 | `SKILL.md:3` |
| B3 | 🟡 | 推理·待实测 | 未声明需要子代理能力，在不支持 `subagent` 的宿主上会直接失败 | 兼容性 | frontmatter |

> 📌 **「定级依据」列是 v2.2 事后补标的**，不代表当时跑过命令：B1/B2 的依据是报告里那两段**可复查的原文对照**（照行号取出即见），B3 当时确实没在任何非 Claude Code 宿主上试过，所以只能挂 🟡。
> 把这份样例直接喂给 v2.2 的报告机检器会**报红**：B1/B2 声称实测，而样例里没有任何「复现命令」小节（这四个字只在本注释里出现过一次）。这是预期行为——样例产于规则之前，机检器不给历史面子。

### B1 · 🔴 裁定方与被审方是同一个 agent

- **证据链**：`SKILL.md:163` 原文——"再起一个子代理（或复用蓝军 agent 通过 `send_message`，让它对第三方报告做裁定——**这更符合"蓝军不信第三方"的设定**）"；对照 `SKILL.md:250` 明令"❌ 让同一个 agent 既审又改又复核 → 它会为自己的结论辩护"。
- **触发条件**：任何一次标准档评审，只要有 T 项针对蓝军原报告的批评。
- **用户可见后果**：针对蓝军的批评被系统性驳回，用户拿到一份"蓝军永远正确"的裁定，误以为闭环成立。
- **修复方向**：第 3 步改为**全新 agent** 担任"中立裁定方"；"蓝军不信第三方"通过提示词立场表达，而非复用身份。`send_message` 复用降级为受限选项并要求声明独立性降级。

### B2 · 🟠 英文触发词不足

- **证据链**：`SKILL.md:3` 的 `description` 中英文触发词仅 `adversarial review` 一条。
- **触发条件**：英文用户说 `code review`、`red team review`、`find bugs in my code`。
- **用户可见后果**：skill 不会被激活，用户以为它不work。
- **修复方向**：补 `red team review` / `pre-release review` / `critique this` / `find bugs in my code`。

### 做得对、值得保持的

- 「能力边界」章节主动声明同模型互搏抓不出共同盲区——**这类"主动认怂"的写法极为罕见且极有价值**，改造时不要删。
- 级联的级别定义（🔴/🟠/🟡）给得具体（"向用户广播错误信息"这种可判定标准），而不是"严重/中等/轻微"这种主观词。

### 未验证项

- 未在非 Claude Code 宿主（Cursor / Codex）上实测 `subagent` 的可用性与行为差异。

## 第三方复核报告（片段）

### 第一部分：蓝军意见逐项验证表

| 编号 | 蓝军意见 | 验证结果 | 证据（文件:行号） |
|---|---|---|---|
| B1 | 裁定方复用蓝军导致自相矛盾 | ✅ 属实落地 | `SKILL.md:163` 与 `SKILL.md:250` 直接冲突 |
| B2 | 英文触发词不足 | ✅ 属实落地 | `SKILL.md:3` |
| B3 | 未声明子代理依赖 | ✅ 属实落地 | frontmatter 无 `compatibility` 字段 |

### 第二部分：新发现的缺陷

**T1 · 🟠 归档策略默认值在开源场景下会制造死链**

- **位置**：`SKILL.md:212`（默认 gitignore `docs/review/`）vs `SKILL.md:228`（警告清理引用）
- **触发链**：开源项目用户按默认策略 gitignore → README 中指向报告的链接失效 → 但 skill 只在第 228 行"提醒"清理，未把"按项目可见性选择默认值"作为决策点 → 用户踩坑。
- **定级**：🟠 —— skill 自己警告过的坑，却把默认值设成了会踩坑的那一侧。
- **可达性**：真实可达，任何公开仓库用户都会遇到。

### 第三部分：蓝军覆盖度稽核

蓝军对"治理 / 可用性 / 兼容性"三项均有实质结论；缺口在**发布工程**维度——归档策略的开源场景（T1）蓝军整项未提。

### 第四部分：发布门结论

- 达到可发布状态？**整改 B1 后可发布。** B1 属流程性缺陷，不改会让整个 skill 的核心卖点失效。
- 硬性阻塞项：无（无 CI、无版本号联动）。

### 对蓝军 B 项的最终状态

| 编号 | 最终状态 |

### 实质分歧

**无。** 三方在 B1 上完全一致——这本身是个信号：**当一个缺陷同时违反了两条明写的规则时，各方都能看到它。**

### 合并执行清单

| 优先级 | 项 | 来源 | 改动量 |
|---|---|---|---|
| P0 | 第 3 步改为中立裁定方 | B1 / T1 | 中（重写提示词 + 新增警示块） |

### 一句话总结三方关系

蓝军定义"修什么"，第三方验证"修没修对、有没有修出新问题"，本报告裁定"双方的结论是否成立"。

## 这轮评审的实际收益

| 指标 | 结果 |
|---|---|
| 发现真实缺陷 | 3 条（1 条 P0 核心机制缺陷） |
| 抓到的最有价值一条 | **B1 自相矛盾**——单人自查几乎必然漏掉，因为写的时候"复用蓝军"看起来是个省事的好主意 |
| 误报 | 0 条被裁定驳回 |

**这正是这个 skill 的价值所在**：它不是让 AI"更仔细地看"，而是建立一个**写的人没有立场去为自己辩护**的结构。
